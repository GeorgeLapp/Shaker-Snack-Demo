# Техническая документация: MDB-RS232 мост Wafer для Cashless-ридеров

**Версия документа:** 3.2 (исправленная и дополненная)  
**Дата:** Декабрь 2025  
**Целевая платформа:** Node.js (ESModules) на контроллере вендингового автомата  
**Фокус:** Исключительно Cashless-устройства (адреса 0x10 для Cashless #1, 0x60 для Cashless #2). Основной пример — Nayax VPOS Touch.  
**Источники:** Все данные взяты исключительно из предоставленных документов (MDB-RS232-Nayax.pdf, MDB-RS232-Data-Format.pdf, MDB-RS232-Manual.pdf, MDB-4.2.pdf). Никакие внешние источники не используются.  
**Важно:** Эта документация полностью самодостаточна — содержит все необходимые определения, расшифровки байтов, форматы данных, примеры и сценарии. Разработчику не требуется обращаться к другим документам.

## 1. Основные термины и определения
- **VMC (Vending Machine Controller)** — контроллер вендингового автомата (ваш Node.js-модуль).
- **MDB (Multi-Drop Bus)** — промышленный протокол для связи VMC с периферийными устройствами (bill acceptor, coin changer, cashless reader).
- **Cashless reader** — устройство безналичной оплаты (картридер, NFC, QR).
- **Мост Wafer MDB-RS232** — аппаратный конвертер MDB ↔ RS232. VMC общается только с мостом по RS232, мост самостоятельно опрашивает (POLL) ридер по MDB.
- **Level 1/2/3** — уровни функциональности cashless-устройства по стандарту MDB 4.2.
- **Scaled value** — цена или баланс в «масштабированном» виде (для учета валюты). Реальная цена = scaled × scaleFactor / (10^decimalPlaces).
- **Activity data** — асинхронные события от ридера (например, карта приложена, продажа одобрена). Имеют префикс Device ID, но не имеют контрольной суммы (CHK).
- **Reply data** — синхронный ответ на команду VMC. Не имеют префикса Device ID, но имеют контрольную сумму (CHK).
- **Cashless Device #1** — первое устройство безналичной оплаты с адресом 0x10.
- **Cashless Device #2** — второе устройство безналичной оплаты с адресом 0x60. Оба устройства могут работать одновременно с разными функциями (например, один для карт, второй для мобильных платежей).
- **32-bit monetary value** — расширенный 32-битный формат для денежных значений, позволяющий представлять суммы до 4294967295 единиц (в масштабированных единицах). При scale factor = 1 и decimal places = 2 это соответствует максимальной сумме 42,949,672.95.

## 2. RS232-интерфейс и формат данных

**Параметры порта (фиксированные):**
- Baud rate: 9600
- Data bits: 8
- Parity: None
- Stop bits: 1
- Flow control: нет

**Отправка (TX: VMC → мост):**  
Чистые бинарные байты (HEX без пробелов, без CRLF).

**Получение (RX: мост → VMC):**  
ASCII-HEX строка: каждый байт представлен двумя символами HEX, байты разделены пробелом (0x20).  
Строка заканчивается CRLF (0x0D 0x0A).

**Важное дополнение:**  
Практически всегда перед CRLF присутствует завершающий пробел (0x20) — парсер должен корректно обрабатывать "хвостовой" 0x20 перед 0x0D 0x0A. Адаптер добавляет `0x20` перед `0x0D 0x0A` для всех ответов (согласно *MDB-RS232-Data-Format.pdf*).  
Это относится и к reply data, и к activity data.  
*Рекомендация:* При парсинге ответов от Wafer всегда использовать `.trim()` для полученной строки перед разбивкой по пробелам, так как `split(' ')` на строке с завершающим пробелом создаст пустой элемент массива, что может вызвать ошибку в конвертере HEX->Int.

После включения питания мост может прислать текстовый баннер (plain ASCII, не HEX):
```
MDB-RS232 V4.2 compatible
```

**Питание моста:** обязательно 24V DC (мин. 20V, ток >3A рекомендуется). 12V недопустимо.

**Пример получения данных от моста (в HEX формате для наглядности):**  
`30 20 30 39 20 46 46 20 0D 0A` → После преобразования ASCII-HEX: "0 09 FF " (CRLF в конце)

**Примечание:** Для Cashless Device #2 все форматы данных аналогичны Cashless Device #1, меняется только префикс Device ID (0x60 вместо 0x10).

## 3. Режимы Level 1/2/3 (MDB 4.2)

Level — это уровень функциональности cashless-устройства, определяющий поддерживаемые возможности протокола.

| Level     | Описание                                                                                                                               | Основные отличия                                                                                                                                                      | Формат Begin Session (10 03 ...)                                                                                                                             | Поддержка Nayax VPOS Touch |
|-----------|----------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------|
| Level 1   | Базовый уровень. Только простые транзакции, 16-битные суммы, без дополнительных метаданных. Нет поддержки дисплея VMC, multi-currency, always idle. | Только базовый vend flow. Funds — всегда 16-бит.                                                                                                                      | FF FF (2 байта доступных средств, scaled)                                                                                                                    | Не используется (Nayax работает минимум Level 3) |
| Level 2   | Расширенный базовый. Добавлены тип платежа и данные платежа. 16-битные суммы.                                                         | Добавлены Payment Type и Payment Data для идентификации типа карты/платежа.                                                                                           | 10 03 FF FF M1 M2 M3 M4 PT PD1 PD2 (funds 16-бит + Payment Media ID(4) + PT + PD(2))                                                                        | Не используется Nayax      |
| Level 3   | Полный уровень. Поддержка 32-битных сумм (опционально), multi-currency, multi-lingual, always idle, negative vend, data entry, file transport. Максимальная совместимость. | Все расширенные опции через EXPANSION. Funds могут быть 32-бит (если включён бит b1). Полная поддержка дисплея VMC.                                                  | В обычном режиме: FF FF M1 M2 M3 M4 PT PD1 PD2 (как Level 2/3); в Expanded Currency Mode (если включены b1 и/или b2 в Enable Options): F1 F2 F3 F4 M1 M2 M3 M4 PT PD1 PD2 L1 L2 C1 C2 OPT | Да, Nayax VPOS Touch работает в Level 3 (в SETUP передаётся 03) |

**Особенности 32-битного формата денежных значений:**
- В 16-битном режиме максимальное значение: 65,535 (0xFFFF) масштабированных единиц
- В 32-битном режиме максимальное значение: 4,294,967,295 (0xFFFFFFFF) масштабированных единиц
- При scale factor = 1 и decimal places = 2:
  - 16-битный режим: максимум 655.35 единиц валюты
  - 32-битный режим: максимум 42,949,672.95 единиц валюты

Определение использования 32-битного формата зависит от бита b1 в Enable Options (17 04 ...)  
Оба Cashless устройства (#1 и #2) могут работать на разных уровнях. VMC должен определять уровень каждого ридера отдельно через SETUP Config Data команду.

## 4. Шесть состояний cashless-ридера (на примере Nayax VPOS Touch)

Ридер имеет шесть рабочих состояний:
1. **Inactive** — после включения или Reset. Ридер неактивен. Переход в Disabled по команде SETUP.
2. **Disabled** — после получения конфигурации от VMC или по команде Disable. Ридер отключён.
3. **Enabled** — после команды Enable. Ожидает карту.
4. **Session Idle** — карта прочитана, сессия начата, ожидает Vend Request.
5. **Vend Request** — получен запрос на продажу от VMC, ожидает одобрения (авторизация на сервере Nayax).
6. **Vend** — продажа выполняется (списание средств).

**Важно:** Cashless reader может требовать подключения к интернету (GSM/3G/4G) для авторизации транзакций на сервере. Без связи ридер может перейти в ошибку или не одобрить платеж.

Cashless Device #2 работает по тем же принципам, но может иметь специфические особенности в зависимости от производителя. Например, некоторые ридеры для мобильных платежей могут переходить в сессию сразу после получения VEND REQUEST без дополнительного подтверждения платежа.

## 5. Device ID и Структура Пакетов (Критически важно)

Мост Wafer различает два типа данных, приходящих к VMC. Это критически важно для парсинга.

1. **Activity Data (Асинхронные события)**  
   Это данные, которые ридер отправляет сам (например, "карта приложена", "just reset", "vend approved").  
   Имеют префикс Device ID: `0x10` (Cashless #1) или `0x60` (Cashless #2).  
   НЕ имеют контрольной суммы (CHK). 

2. **Reply Data (Синхронные ответы)**  
   Это данные, которые приходят в ответ на конкретную команду VMC (например, ответ на `SETUP`, ответ на `EXPANSION Request ID`).  
   НЕ имеют префикса Device ID.  
   ИМЕЮТ контрольную сумму (CHK) в конце. 

| Тип данных        | Префикс ID (10/60) | Checksum (CHK) | Пример (Cashless #1) |
|-------------------|-------------------|----------------|----------------------|
| Activity (Poll)   | ЕСТЬ              | НЕТ            | 10 03 ... (Begin Session) |
| Reply (Response)  | НЕТ               | ЕСТЬ           | 01 03 ... CHK (Reader Config) |

ACK (00) / NAK (FF) приходят без префикса и без CHK.

## 6. Контрольные суммы (CHK)

CHK = 8-битная сумма всех байт сообщения до CHK (арифметическая сумма, без carry, & 0xFF).

**Правила применения:**
- Reply data (ответ на команду VMC) — CHK присутствует как последний байт.
- Activity data (события от ридера) — без CHK. Адаптер не добавляет CHK к асинхронным событиям.
- ACK/NAK (00 или FF) — без CHK.
- VMC не добавляет CHK при отправке — мост делает это автоматически на MDB-шине.

**Примеры вычисления:**  
Ответ Nayax на SETUP (Reply Data): `01 03 11 56 01 02 28 0D A3`  
Сумма: 0x01 + 0x03 + 0x11 + 0x56 + 0x01 + 0x02 + 0x28 + 0x0D = 0xA3 ✓

В Node.js:
```javascript
function calculateCHK(bytes) {
  return bytes.reduce((sum, b) => sum + b, 0) & 0xFF;
}
```

## 8. Подробное описание каждой команды и ответа

> **Уточнение по ответам:** для команд с типом ответа **ACK/NAK (No Data response)** ожидаемый ответ — `00` (ACK). В случае отказа/ошибки устройство может вернуть **NAK = FF** (код ошибки), который следует трактовать как “команда не принята/не выполнена”. Для команд с типом ответа **Reply Data** ожидается многобайтовый ответ, заканчивающийся `CHK`.


### 8.1 RESET (10 для Cashless #1, 60 для Cashless #2)

**Описание:** Полный сброс ридера. Переводит в состояние Inactive.
**Формат отправки:** один байт 0x10 (Cashless #1) или 0x60 (Cashless #2).
**Ожидаемый ответ:** 00 (ACK) или NAK.
**Возможное activity:** 10 00 или 60 00 — Just Reset. (Обратите внимание: это два байта в HEX: ID + Code 00).

**Пример кода для Cashless #1:**

```javascript
port.write(Buffer.from([0x10]));
```

**Пример кода для Cashless #2:**

```javascript
port.write(Buffer.from([0x60]));
```

### 8.2 SETUP Config Data (11 00 Y2 Y3 Y4 Y5 для #1, 61 00 Y2 Y3 Y4 Y5 для #2)

**Описание:** Передаёт VMC-конфигурацию ридеру. Обязательна после Reset. Переводит ридер в Disabled.

**Полный разбор параметров отправки:**

* 0x11 или 0x61 — команда SETUP
* 0x00 — субкоманда Config Data
* Y2 — Feature Level VMC. Назначение: сообщает ридеру максимальный поддерживаемый уровень протокола VMC. Используется для совместимости. Значения: 0x01 (Level 1), 0x02 (Level 2), 0x03 (Level 3).
* Y3 — Columns on display. Назначение: количество колонок на дисплее VMC. Используется ридером для форматирования сообщений (Display Request). 0x00 = нет дисплея.
* Y4 — Rows on display. Назначение: количество строк на дисплее VMC. Аналогично Y3. 0x00 = нет дисплея.
* Y5 — Display Information byte. Назначение: тип поддерживаемых символов на дисплее VMC. Используется для отправки корректных сообщений.

**Все возможные значения Y5 (битовая маска):**
Биты 7–3: зарезервированы, должны быть 00000. Биты 2–0 (yyy): тип символов.

| yyy (bin) | yyy (hex) | Значение                                 | Назначение                |
| --------- | --------- | ---------------------------------------- | ------------------------- |
| 000       | 0x00      | Цифры + заглавные буквы + пробел + точка | Базовый текстовый дисплей |
| 001       | 0x01      | Полный ASCII                             | Полный набор символов     |
| 010–111   | 0x02–0x07 | Unassigned                               | Не использовать           |

**Ответ — Reader Config Data (Reply Data, с CHK, без префикса):**
Формат (полный разбор всех полей по MDB 4.2 с примерами Nayax):
01 Z2 Z3 Z4 Z5 Z6 Z7 Z8 [дополнительные байты] CHK

* 0x01 — идентификатор Reader Config Data
* Z2 — Feature Level ридера. Назначение: максимальный уровень, поддерживаемый ридером. Используется VMC для выбора функций.
* Z3 Z4 — Country/Currency Code (packed BCD, 2 байта). Назначение: код страны/валюты, закодированный в packed BCD (возможны варианты по ведущей BCD-цифре; для Level 3 по стандарту обязателен ISO 4217 numeric).
* Z5 — Scale Factor. Назначение: множитель для масштабирования цен. **Реальная цена = scaled × scale / (10^decimal).** Обычно 0x01.
* Z6 — Decimal Places. Назначение: количество знаков после запятой. Обычно 0x02 (центы).
* Z7 — Application Maximum Response Time. Назначение: Максимальное время (в **секундах**), в течение которого ридер может **не отвечать** на команды или POLL (например, пока выполняет длительную обработку — авторизацию и т.п.). Для cashless по умолчанию Maximum Non-Response Time = **5 сек**, а если **Z7 больше 5**, то **Z7 заменяет дефолт**. Если ридер **не отвечает** дольше этого времени (нет ACK/NAK/сообщения), он считается **off-line**. Также, если не указано иначе, VMC должен использовать это же значение как **таймаут ожидания ответа** для команд, которые **возвращают данные**.
* Z8 — Miscellaneous Options. Назначение: битовая маска дополнительных возможностей ридера.

**Детальное описание битов Z8 (по MDB 4.2):**

* b0 (бит 0): Возможность возврата средств (refund). Если установлен (1), ридер способен восстанавливать средства на платёжное средство/аккаунт. Если 0 — refunds не запрашивать.
* b1 (бит 1): Поддержка multi-vend. Если 1 — multivend возможен (несколько покупок в одной сессии). Если 0 — завершать сессию после каждой продажи.
* b2 (бит 2): Наличие дисплея ридера. Если 1 — у ридера есть собственный дисплей. Если 0 — дисплея нет.
* b3 (бит 3): Поддержка подкоманды VEND/CASH SALE. Если 1 — поддерживает. Если 0 — не поддерживает.
* b4-b7: должны быть 0; будущие опции покрываются через EXPANSION option bits.

**Пример Nayax для Cashless #1 (Reply):**
01 03 11 56 01 02 28 0D A3
Расшифровка: Level 3, country/currency code (packed BCD) 11 56, scale 1, decimal 2, max time 0x28 (40 секунд), misc 0x0D (биты 0, 2 и 3 установлены), CHK 0xA3.

**Пример кода для Cashless #1:**

```javascript
port.write(Buffer.from([0x11, 0x00, 0x03, 0x00, 0x00, 0x02]));
```

**Пример кода для Cashless #2:**

```javascript
port.write(Buffer.from([0x61, 0x00, 0x03, 0x00, 0x00, 0x02]));
```

### 8.3 SETUP Max/Min Price (11 01 XX XX YY YY для #1, 61 01 XX XX YY YY для #2)

**Описание:** Установка максимальной и минимальной цены продажи (scaled, 16-бит).
**Разбор байтов:**

* XX XX — Max Price (scaled, big-endian)
* YY YY — Min Price (scaled, big-endian)

**Рекомендуется:**
11 01 FF FF 00 00 (Cashless #1) или 61 01 FF FF 00 00 (Cashless #2) (max ≈655.35, min 0 при scale=1, decimal=2).
**Ответ:** 00 (ACK) или NAK.

**Описание для 32-битного режима:**
Если VMC включает 32-битный режим, он **должен** отправить эту команду при инициализации в 16-битном формате, а **после** команды `ENABLE OPTIONS (17 04)` — отправить её повторно в 32-битном формате (Expanded Currency Mode).
В 32-битном режиме формат команды (Expanded Currency Mode):
11 01 XX XX XX XX YY YY YY YY CC CC (для Cashless #1)
61 01 XX XX XX XX YY YY YY YY CC CC (для Cashless #2)
где:

* XX XX XX XX — Max Price (scaled, 32-бит, big-endian)
* YY YY YY YY — Min Price (scaled, 32-бит, big-endian)
* CC CC — Currency Code (ISO 4217 numeric, packed BCD с ведущей цифрой 1)

В расширенном формате максимальная цена может достигать 4,294,967,295 (0xFFFFFFFF) масштабированных единиц. При scale=1 и decimal=2 это соответствует 42,949,672.95 единиц валюты.

**Пример кода для Cashless #1:**

```javascript
port.write(Buffer.from([0x11, 0x01, 0xFF, 0xFF, 0x00, 0x00]));
```

**Пример кода для Cashless #2:**

```javascript
port.write(Buffer.from([0x61, 0x01, 0xFF, 0xFF, 0x00, 0x00]));
```

### 8.4 EXPANSION Request ID (17 00 для Cashless #1, 67 00 для Cashless #2)

### Назначение

Команда `EXPANSION Request ID` используется для:

1. **передачи ридеру идентификационных данных VMC** (manufacturer/serial/model/software version),
2. **получения идентификационных данных ридера** в формате `Peripheral ID (09h)`,
3. получения для Level 03 ридеров поля **Optional Feature Bits (32 бита)**, которое является **основой для формирования** команды
   `EXPANSION Optional Feature Bit Enable (17 04 / 67 04)`.

---

### Строгое правило наличия Optional Feature Bits (32-bit Optional Feature Set)

Поле **Optional Feature Bits (4 байта)** присутствует **только при одновременном выполнении следующих условий**:

1. VMC ранее отправил `SETUP Config Data (11 00 ... / 61 00 ...)` и указал `Y2 = 0x03` (**Feature Level = 3**),
2. ридер поддерживает **Level 03** (и формирует расширенный `Peripheral ID`).

Если `Y2 = 0x01` или `Y2 = 0x02`, то **Optional Feature Bits не передаются**, даже если ридер физически является Level 03.

# A) Формат отправляемой команды (байты, которые VMC пишет в мост)

#### A1. Cashless #1 (адрес устройства при отправке через мост = 0x10)

**Формат команды (31 байт):**

```
17 00  M1 M2 M3  S1 S2 S3 S4 S5 S6 S7 S8 S9 S10 S11 S12  N1 N2 N3 N4 N5 N6 N7 N8 N9 N10 N11 N12  V1 V2
```

**Таблица полей команды (TX → мост):**

| Offset | Длина | Поле   | Имя       | Формат     | Описание                                                  |
| -----: | ----: | ------ | --------- | ---------- | --------------------------------------------------------- |
|      0 |     1 | CMD    | `0x17`    | HEX        | Команда EXPANSION для Cashless #1 (адресация через мост). |
|      1 |     1 | SUB    | `0x00`    | HEX        | Подкоманда `Request ID`.                                  |
|      2 |     3 | MFG    | `M1..M3`  | ASCII      | **Manufacturer Code VMC** (3 символа).                    |
|      5 |    12 | SERIAL | `S1..S12` | ASCII      | **Serial Number VMC** (12 символов).                      |
|     17 |    12 | MODEL  | `N1..N12` | ASCII      | **Model Number VMC** (12 символов).                       |
|     29 |     2 | SWVER  | `V1 V2`   | packed BCD | **Software Version VMC** (2 байта, BCD).                  |

**Итоговая длина:** `2 + 3 + 12 + 12 + 2 = 31 байт`

---

#### A2. Cashless #2 (адрес устройства при отправке через мост = 0x60)

**Формат команды (31 байт):**

```
67 00  M1 M2 M3  S1..S12  N1..N12  V1 V2
```

**Таблица полей команды (TX → мост):**

| Offset | Длина | Поле   | Имя       | Формат     | Описание                                                  |
| -----: | ----: | ------ | --------- | ---------- | --------------------------------------------------------- |
|      0 |     1 | CMD    | `0x67`    | HEX        | Команда EXPANSION для Cashless #2 (адресация через мост). |
|      1 |     1 | SUB    | `0x00`    | HEX        | Подкоманда `Request ID`.                                  |
|      2 |     3 | MFG    | `M1..M3`  | ASCII      | Manufacturer Code VMC (3 символа).                        |
|      5 |    12 | SERIAL | `S1..S12` | ASCII      | Serial Number VMC (12 символов).                          |
|     17 |    12 | MODEL  | `N1..N12` | ASCII      | Model Number VMC (12 символов).                           |
|     29 |     2 | SWVER  | `V1 V2`   | packed BCD | Software Version VMC.                                     |

---

#### A3. Правила заполнения ASCII-полей (MFG/SERIAL/MODEL)

**Manufacturer Code (3 байта ASCII)**

* Ровно 3 символа ASCII.
* Примеры:

  * `"NYX"` → `4E 59 58`
  * `"NEC"` → `4E 45 43`

**Serial Number (12 байт ASCII)**

* Ровно 12 символов.
* Допускаются:

  * пробел `0x20`,
  * символ `"0"` = `0x30`,
  * любые ASCII цифры/буквы.
* Если строка короче 12 символов — VMC **дополняет справа** пробелами `0x20` или нулями `0x30`.

**Model Number (12 байт ASCII)**

* Ровно 12 символов.
* Аналогично, если меньше — дополняется пробелами.

---

#### A4. Правила заполнения SWVER (2 байта packed BCD)

`V1 V2` — два байта BCD:

* каждый байт содержит **две десятичные цифры**:

  * старший nibble = десятки,
  * младший nibble = единицы.

Примеры:

* версия `1.00` → `01 00`
* версия `0.11` → `00 11`
* версия `12.34` → `12 34`

# B) Формат получаемого ответа от моста (Reply Data Peripheral ID = 09h)

#### B1. Общие правила ответа (важно для парсинга через мост)

Для команды `Request ID` **ридер возвращает Reply Data**, а **мост транслирует его наружу** в сторону VMC так, что:

* ответ **не является activity** (то есть **не начинается** с `10 ...` или `60 ...`);
* ответ — это именно “Reply Data” с полезной нагрузкой и `CHK` в конце;
* **последний байт ответа = CHK** (контрольная сумма);
* если ответ “multi-message”, то VMC **после каждого блока** данных должен отправлять `00 (ACK)` в мост.

---

#### B2. Peripheral ID (09h) — структура ответа

Ответ называется **Peripheral ID** и начинается байтом `0x09`.

---

#### B3. Формат Peripheral ID для Level 01/02 (и для Level 03, если VMC указал Level 01/02)

**Формат данных (30 байт + CHK):**

```
09  R1 R2 R3  S1..S12  N1..N12  V1 V2  CHK
```

**Таблица полей ответа (RX ← мост):**

| Offset | Длина | Поле   | Имя       | Формат     | Описание                                                                    |
| -----: | ----: | ------ | --------- | ---------- | --------------------------------------------------------------------------- |
|      0 |     1 | RESP   | `0x09`    | HEX        | Код Reply Data: `Peripheral ID`.                                            |
|      1 |     3 | MFG    | `R1..R3`  | ASCII      | **Manufacturer Code ридера** (3 символа).                                   |
|      4 |    12 | SERIAL | `S1..S12` | ASCII      | **Serial Number ридера** (12 символов).                                     |
|     16 |    12 | MODEL  | `N1..N12` | ASCII      | **Model Number ридера** (12 символов).                                      |
|     28 |     2 | SWVER  | `V1 V2`   | packed BCD | **Software Version ридера**.                                                |
|     30 |     1 | CHK    | `CHK`     | HEX        | Checksum: сумма всех байтов с offset 0 по offset 29 включительно (без CHK). |

---

#### B4. Формат Peripheral ID для Level 03 (когда VMC указал Level 03)

**Формат данных (34 байта + CHK):**

```
09  R1 R2 R3  S1..S12  N1..N12  V1 V2  F1 F2 F3 F4  CHK
```

**Таблица полей ответа (RX ← мост):**

| Offset | Длина | Поле    | Имя       | Формат     | Описание                                                                                                   |
| -----: | ----: | ------- | --------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
|      0 |     1 | RESP    | `0x09`    | HEX        | Код Reply Data: `Peripheral ID`.                                                                           |
|      1 |     3 | MFG     | `R1..R3`  | ASCII      | Manufacturer Code ридера (3 символа).                                                                      |
|      4 |    12 | SERIAL  | `S1..S12` | ASCII      | Serial Number ридера (12 символов).                                                                        |
|     16 |    12 | MODEL   | `N1..N12` | ASCII      | Model Number ридера (12 символов).                                                                         |
|     28 |     2 | SWVER   | `V1 V2`   | packed BCD | Software Version ридера.                                                                                   |
|     30 |     4 | OPTBITS | `F1..F4`  | bitfield   | **Optional Feature Bits (32 бита)** — присутствуют **строго только если** `Y2=0x03` в `SETUP Config Data`. |
|     34 |     1 | CHK     | `CHK`     | HEX        | Checksum: сумма всех байтов с offset 0 по offset 33 включительно (без CHK).                                |

# C) Подробная интерпретация Optional Feature Bits (F1..F4)

#### C1. Представление и порядок

`F1 F2 F3 F4` — 4 байта (в порядке **старший байт → младший байт**).

* `F1` содержит **биты 31..24**
* `F2` содержит **биты 23..16**
* `F3` содержит **биты 15..8**
* `F4` содержит **биты 7..0**

То есть **bit31 передаётся первым**, **bit0 — последним**.

---

#### C2. Значения битов (Level 03 optional features)

|     Бит | Маска (hex)  | Назначение                     | Что меняется в протоколе                                           |
| ------: | ------------ | ------------------------------ | ------------------------------------------------------------------ |
|      b0 | `0x00000001` | File Transport Layer (FTL)     | Доступны команды передачи файлов (редко используется в vending).   |
|      b1 | `0x00000002` | 32-bit money mode              | Денежные значения могут стать 32-битными (в зависимых сообщениях). |
|      b2 | `0x00000004` | Multi-currency / multi-lingual | Разрешает расширенные валюты/языки (expanded currency mode).       |
|      b3 | `0x00000008` | Negative vend                  | Разрешает отрицательные продажи/коррекции.                         |
|      b4 | `0x00000010` | Data Entry                     | Разрешает запросы ввода данных пользователем.                      |
|      b5 | `0x00000020` | Always Idle                    | Разрешает сценарий, где VEND может инициироваться при idle-ридере. |
| b6..b31 | —            | Reserved/Unused                | Должны игнорироваться и быть 0.                                    |

---

#### C3. Связь с EXPANSION Enable Options (17 04 / 67 04)

**`Optional Feature Bits` — это “что ридер умеет”**, а `Enable Options (17 04 / 67 04)` — **что VMC просит включить**.

То есть:

1. VMC читает `F1..F4` из `Peripheral ID (09h)`;
2. VMC формирует маску `B1..B4`:

   * `Bbit = 1` только если:

     * `Fbit = 1` (ридер поддерживает),
     * и VMC хочет включить.
3. VMC отправляет `17 04 B1 B2 B3 B4` или `67 04 B1 B2 B3 B4`.

После reset — **все optional features выключены**, даже если поддерживаются.

---

# D) Контрольная сумма CHK (как учитывать)

В ответах Reply Data от моста последний байт `CHK`.

**Правило:**
`CHK = SUM(all data bytes) mod 256`
где в “data bytes” входят все байты ответа **кроме самого CHK**.

Пример (схематично):

* получили: `09 ... ... CHK`
* суммируете байты от `09` до последнего data-байта включительно,
* берёте младший байт суммы,
* сравниваете с `CHK`.

---

# E) Multi-message ответ и подтверждение блоков

Если мост отдаёт `Peripheral ID` частями (multi-message), VMC обязан:

1. принять очередной блок Reply Data;
2. проверить CHK этого блока;
3. отправить `00 (ACK)` в мост;
4. принять следующий блок.

    |  |   NYX        330823184108             DMX - 2011        v1.00

#### F2. Пример получения Peripheral ID (Level 03)

Где `00 00 00 20` означает включаемую возможность **b5 Always Idle** (как поддерживаемую опцию), которую затем можно активировать через `Enable Options`.


### 8.5 EXPANSION Enable Options (17 04 B1 B2 B3 B4 для #1, 67 04 B1 B2 B3 B4 для #2)

**Описание:** Включение дополнительных функций ридера (32-битная маска опций (Y2–Y5 / B1–B4) передаётся в порядке старший→младший байт; биты — по убыванию: bit31 первым, bit0 — последним). После reset все опции выключены. VMC отправляет маску бит, которые хочет включить (1 = enable).

**Полная таблица всех опций (по MDB 4.2):**

| Бит    | Маска (hex) | Назначение                             | Использование и влияние                                                                                                         |
| ------ | ----------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| b0     | 0x00000001  | File Transport Layer supported         | Для передачи файлов (обновление прошивки ридера)                                                                                |
| b1     | 0x00000002  | 32-bit money mode                      | Включает 32-битные денежные поля в командах/ответах, использующих monetary format (в т.ч. VEND Request/Approved, REVALUE и др.) |
| b2     | 0x00000004  | Multi-currency / multi-lingual support | Поддержка нескольких валют и языков (Expanded Currency Mode)                                                                    |
| b3     | 0x00000008  | Allow Negative Vend                    | Разрешает Negative Vend                                                                                                         |
| b4     | 0x00000010  | Allow Data Entry Vend                  | Разрешает ввод данных (Data Entry)                                                                                              |
| b5     | 0x00000020  | Allow Always Idle mode                 | Ридер может работать в Always Idle (Product First может начинаться с VEND Request)                                              |
| b6–b31 | —           | Зарезервировано                        | Должны быть 0                                                                                                                   |

**Пример:** включить только b0 (0x00000001) → 17 04 00 00 00 01; включить b5 (0x00000020) → 17 04 00 00 00 20.

**Рекомендуемый для Nayax (Cashless #1):**
17 04 00 00 00 20 (только Always Idle) или 17 04 00 00 00 22 (Always Idle + 32-bit money).
**Рекомендуемый для Cashless #2:**
67 04 00 00 00 20 (только Always Idle) или 67 04 00 00 00 22 (Always Idle + 32-bit money).

**Предупреждение:** Не включайте неподдерживаемые опции — ридер может зависнуть или не ответить.
**Ответ:** 00 (ACK) или NAK.

**Пример кода для Cashless #1:**

```javascript
port.write(Buffer.from([0x17, 0x04, 0x00, 0x00, 0x00, 0x20])); // Always Idle
```

**Пример кода для Cashless #2:**

```javascript
port.write(Buffer.from([0x67, 0x04, 0x00, 0x00, 0x00, 0x20])); // Always Idle
```

### 8.9 VEND Request (13 00 ... для #1, 63 00 ... для #2)

**Описание:** Запрос на продажу товара (Product First сценарий). В рамках Product First отправляется **после Begin Session (обычный сценарий)** **или может отправляться до Begin Session (если ридер находится в Always Idle, тогда Begin Session приходит после VEND Request)** и содержит цену и номер товара. **Формат зависит от режима Expanded Currency Mode** (включён ли он через `EXPANSION Optional Feature Bit Enable (17 04)`): в обычном режиме цена передаётся 16-бит (`Y2–Y3`), а в Expanded Currency Mode — 32-бит (`Y2–Y5`), с соответствующим сдвигом поля номера товара.

**Вариант А: Обычный режим (16-bit)**
Используется, если бит b1 (32-bit) и b2 (Multi-currency) НЕ были включены.
**Формат:** `13 00 P1 P2 I1 I2`

* 0x13 — команда VEND (0x63 для Cashless #2)
* 0x00 — субкоманда Request
* P1 P2 — Цена (16 бит, scaled, big-endian)
* I1 I2 — Номер товара (16 бит, big-endian)

**Вариант Б: Expanded Currency Mode (32-bit)**
Используется, если бит b1 или b2 БЫЛИ включены в команде `ENABLE OPTIONS`.
**Формат:** `13 00 P1 P2 P3 P4 I1 I2`

* 0x13 — команда VEND (0x63 для Cashless #2)
* 0x00 — субкоманда Request
* P1 P2 P3 P4 — Цена (32 бита, scaled, big-endian)
* I1 I2 — Номер товара (16 бит, big-endian)

**Ответ:** 00 (ACK) или NAK. Далее возможна асинхронная активность: 10 05 ... или 60 05 ... (Approved) или 10 06 ... / 60 06 ... (Denied).

**Пример кода для Cashless #1:**

```javascript
const priceScaled = 500; // 5.00
const item = 1;
const is32BitMode = true; // Set based on enabled options

if (is32BitMode) {
  // Expanded 32-bit mode
  port.write(Buffer.from([
    0x13, 0x00, 
    (priceScaled >> 24) & 0xFF, (priceScaled >> 16) & 0xFF, (priceScaled >> 8) & 0xFF, priceScaled & 0xFF, 
    (item >> 8) & 0xFF, item & 0xFF
  ]));
} else {
  // Normal 16-bit mode
  port.write(Buffer.from([
    0x13, 0x00, 
    (priceScaled >> 8) & 0xFF, priceScaled & 0xFF, 
    (item >> 8) & 0xFF, item & 0xFF
  ]));
}
```

**Пример кода для Cashless #2:**

```javascript
const priceScaled = 500; // 5.00
const item = 1;
// Same logic, but command starts with 0x63
if (is32BitMode) {
   // ... 0x63, 0x00, P1, P2, P3, P4, I1, I2 ...
} else {
   // ... 0x63, 0x00, P1, P2, I1, I2 ...
}
```

**Пример кода для Cashless #1:**

```javascript
port.write(Buffer.from([0x13, 0x05, 0x01, 0xF4])); // 5.00
```

**Пример кода для Cashless #2:**

```javascript
port.write(Buffer.from([0x63, 0x05, 0x01, 0xF4])); // 5.00
```

### 8.14 REVALUE Limit Request (15 01 для #1, 65 01 для #2)

**Описание:** Запрос лимита пополнения (revalue limit) для текущего состояния платёжного носителя (payment media). Команда нужна, чтобы VMC заранее знал **максимальную сумму**, которую ридер согласится принять по `REVALUE Request (15 00/65 00)` в данный момент (особенно важно, если параллельно используется купюроприёмник/монетник с крупными номиналами).
**Когда использовать:** если предполагается пополнение, VMC должен отправлять `REVALUE Limit Request` **после Begin Session** и **до** фактического `REVALUE Request`.

**Смысл результата (что означает “лимит”):**
Ридер возвращает лимит как **scaled value**, вычисленный как:

> `revalueLimitScaled = (maxAllowedBalanceScaled - currentBalanceScaled)`

Если платёжного носителя нет/он недоступен (например, не приложена карта), ридер вместо лимита отвечает кодом отказа `REVALUE DENIED (0x0E)`.

#### Формат команды (байты, которые отправляются в мост)

* **Cashless #1:** `15 01`
* **Cashless #2:** `65 01`

Где:

* `15` / `65` — команда **REVALUE** для cashless #1 / #2
* `01` — подкоманда **Revalue Limit Request**

#### Ожидаемый ответ

**Тип ответа:** Reply Data (многобайтовый) **или** однобайтовый отказ.

1. **Успешный ответ (Reply Data): `REVALUE LIMIT AMOUNT (0x0F)`**

* Первый байт ответа: `0x0F` — `Revalue Limit Amount`
* Далее — поле лимита в scaled-формате; **длина поля зависит от режима Expanded Currency Mode**
* Последний байт в reply — `CHK` (sum check) для многобайтовых ответов

2. **Отказ (No Data / single-byte): `REVALUE DENIED (0x0E)`**

* Однобайтовый ответ: `0x0E`
* `CHK` не добавляется (так как ответ однобайтовый)

#### Формат `REVALUE LIMIT AMOUNT (0x0F)` по режимам (ценовые/денежные форматы)

##### Режим A — Expanded Currency Mode **выключен** (обычный “16-bit money”)

**Ответ (Reply Data):**

```
0F L1 L2 CHK
```

Где:

* `0F` — Revalue Limit Amount
* `L1 L2` — `Revalue Limit Value` (scaled), **16-бит**, порядок **big-endian** (`L1` старший байт)
* `CHK` — контрольная сумма (сумма всех байтов ответа **в hex**, без учёта самого `CHK`)

**Пример интерпретации:**
Если пришло `0F 01 F4 XX`, то `limitScaled = 0x01F4 = 500`.

##### Режим B — Expanded Currency Mode **включён** (Level 3, “32-bit money / Expanded Currency Mode”)

**Ответ (Reply Data):**

```
0F L1 L2 L3 L4 CHK
```

Где:

* `0F` — Revalue Limit Amount
* `L1 L2 L3 L4` — `Revalue Limit Value` (scaled), **32-бит**, порядок **big-endian** (`L1` старший байт)
* `CHK` — контрольная сумма (sum check)

**Пример интерпретации:**
Если пришло `0F 00 00 01 F4 XX`, то `limitScaled = 0x000001F4 = 500`.

#### Связь с Scale Factor / Decimal Places (как получить “реальную сумму”)

Поле лимита (`limitScaled`) — это **масштабированное значение**. Реальная сумма в валюте вычисляется по параметрам из `Reader Config Data`:

* `scale = Z5 (Scale Factor)`
* `decimal = Z6 (Decimal Places)`

Формула:

```
limitReal = limitScaled * scale / (10^decimal)
```

**Пример:** `scale=1`, `decimal=2`, `limitScaled=500` → `limitReal = 500 * 1 / 100 = 5.00`.

#### Примеры (оба режима) — Cashless #1 и Cashless #2

##### Отправка запроса лимита

**Cashless #1**

```javascript
port.write(Buffer.from([0x15, 0x01]));
```

**Cashless #2**

```javascript
port.write(Buffer.from([0x65, 0x01]));
```

##### Пример обработки ответа (универсально для 16-bit и 32-bit)

```javascript
function parseRevalueLimitReply(buf, is32BitMode, scale, decimal) {
  // buf: bytes of reply data (без префикса устройства), уже декодированные из ASCII-HEX в байты
  // Возможные варианты:
  // - [0x0E] -> REVALUE DENIED
  // - [0x0F, ..., CHK] -> REVALUE LIMIT AMOUNT

  if (buf.length === 1 && buf[0] === 0x0E) {
    return { ok: false, code: 'REVALUE_DENIED' };
  }

  if (buf.length < 1 || buf[0] !== 0x0F) {
    return { ok: false, code: 'UNEXPECTED_REPLY' };
  }

  let limitScaled;
  if (is32BitMode) {
    // 0F + 4 bytes + CHK
    if (buf.length < 6) return { ok: false, code: 'TRUNCATED_REPLY' };
    limitScaled = (buf[1] << 24) | (buf[2] << 16) | (buf[3] << 8) | buf[4];
  } else {
    // 0F + 2 bytes + CHK
    if (buf.length < 4) return { ok: false, code: 'TRUNCATED_REPLY' };
    limitScaled = (buf[1] << 8) | buf[2];
  }

  const limitReal = (limitScaled * scale) / Math.pow(10, decimal);
  return { ok: true, limitScaled, limitReal };
}
```

#### Практические правила использования

1. Перед тем как принимать купюры/монеты под пополнение, VMC должен запросить лимит `15 01/65 01` и ограничить принимаемую сумму так, чтобы итоговое пополнение **не превышало** `limitScaled`.
2. Если пришёл `0x0E (REVALUE DENIED)`, значит сейчас пополнение невозможно (нет payment media / ридер не готов) — VMC не должен продолжать сценарий revalue.
3. Длина поля лимита (16 vs 32) должна соответствовать активному режиму денежных форматов (Expanded Currency Mode), выбранному через `EXPANSION Enable Options (17 04/67 04)` и поддержанному ридером.

### 8.15 REVALUE Request (15 00 ... для #1, 65 00 ... для #2)

**Описание:** Запрос на пополнение (revalue) платёжного носителя (payment media) на сумму, указанную VMC (revalue amount).
**Ограничение:** сумма revalue не должна превышать лимит, возвращаемый командой **REVALUE LIMIT REQUEST**.
**Ответ:** `Revalue Approved (0x0D)` или `Revalue Denied (0x0E)` (может прийти сразу или после POLL).

**Формат команды (байты, которые отправляются в мост):**

* **Cashless #1:** `15 00 <RevalueAmountScaled>`
* **Cashless #2:** `65 00 <RevalueAmountScaled>`

Где:

* `15` / `65` — команда **REVALUE** для cashless #1 / #2
* `00` — подкоманда **Revalue Request**
* `<RevalueAmountScaled>` — сумма пополнения в **scaled**-формате:

  * **Expanded Currency Mode выключен:** `Y2–Y3` (16-бит, big-endian)
    → команда имеет вид: `15 00 P1 P2` / `65 00 P1 P2`
  * **Expanded Currency Mode включён:** `Y2–Y5` (32-бит, big-endian)
    → команда имеет вид: `15 00 P1 P2 P3 P4` / `65 00 P1 P2 P3 P4`

---

#### Пример для Cashless #1 — Expanded Currency Mode **выключен** (16-бит сумма)

Сумма (scaled) = `0x01F4` (500)

```javascript
// 15 00 01 F4
port.write(Buffer.from([0x15, 0x00, 0x01, 0xF4]));
```

#### Пример для Cashless #2 — Expanded Currency Mode **выключен** (16-бит сумма)

```javascript
// 65 00 01 F4
port.write(Buffer.from([0x65, 0x00, 0x01, 0xF4]));
```

---

#### Пример для Cashless #1 — Expanded Currency Mode **включён** (32-бит сумма)

Сумма (scaled) = `0x000001F4` (500)

```javascript
// 15 00 00 00 01 F4
port.write(Buffer.from([0x15, 0x00, 0x00, 0x00, 0x01, 0xF4]));
```

#### Пример для Cashless #2 — Expanded Currency Mode **включён** (32-бит сумма)

```javascript
// 65 00 00 00 01 F4
port.write(Buffer.from([0x65, 0x00, 0x00, 0x00, 0x01, 0xF4]));
```

## 9. Подробное описание Activity data (асинхронные события)

### 9.1 Подробное описание каждого Activity data кода

#### 9.1.1 Just Reset (10 00 / 60 00)

**Описание:** Ридер только что сбросился (после команды Reset или power-on).
**Формат:** 10 00 (Cashless #1) или 60 00 (Cashless #2). Это два байта.
**Особенности:**

* После получения этого события VMC должен повторно инициализировать ридер (SETUP Config Data, SETUP Max/Min Price, etc.).
* Для Cashless Device #2 используется префикс 60 вместо 10.

#### 9.1.2 Reader Config Data (Activity: 10 01 ... / 60 01 ...)

**Описание:** Дублирует конфигурационные данные ридера.
**Формат:** 10 01 `01 Z2 Z3 Z4 Z5 Z6 Z7 Z8 ...` (**без CHK**) или 60 01 `01 ...` (**без CHK**).
**Полный разбор байтов:**

* 10 01 или 60 01 — префикс и код события
* Далее идёт payload **Reader Config Data**, идентичный Reply Data на SETUP Config Data, но **без CHK** в конце.
  **Особенности:**
* Может приходить асинхронно (например, если ридер сначала вернул `00 (ACK)`, а затем “дослал” конфиг как activity).

#### 9.1.3 Display Request (10 02 TT <data> / 60 02 TT <data>)

**Описание:** Ридер просит VMC показать сообщение на дисплее.
**Формат:** 10 02 TT D1 D2 ... Dn (Cashless #1) или 60 02 TT D1 D2 ... Dn (Cashless #2), где:

* TT — время отображения в 0.1 секундах (00..FF)
* D1...Dn — ASCII-текст (длина = columns × rows из SETUP)

**Пример:** 10 02 32 49 6E 73 65 72 74 20 63 61 72 64 20 = "Insert card " (с временем 5 секунд)
**Особенности:**

* Всегда начинается с Device ID (10 или 60).
* Не имеет CHK в конце.
* Если в SETUP было установлено Y3=0 и/или Y4=0 (нет дисплея), ридер не должен отправлять этого события.
* Длина текста строго определяется количеством колонок и строк из SETUP Config Data.
* Для Cashless Device #2 все байты идентичны, отличается только префикс.

#### 9.1.4 Begin Session (10 03 ... / 60 03 ...)

**Описание:** Карта/платёжное средство прочитано, сессия начата. Funds — доступный баланс (scaled).
**Формат для Level 1 (16-бит):** `10 03 F1 F2` (Cashless #1) или `60 03 F1 F2` (Cashless #2)
**Формат для Level 2/3 (16-бит, не expanded):** `10 03 F1 F2 M1 M2 M3 M4 PT PD1 PD2` (или с префиксом 60 для Cashless #2)
**Формат для Level 3 Expanded Currency Mode:** `10 03 F1 F2 F3 F4 M1 M2 M3 M4 PT PD1 PD2 L1 L2 C1 C2 OPT` (или с префиксом 60 для Cashless #2)
**Без CHK.**

**Полный разбор байтов:**

* **Funds Available (scaled):**

  * Level 1/2/3 (не expanded): `F1 F2` (16-бит, big-endian)

    * `0xFFFE` = максимум “known credit” в scaled units
    * `0xFFFF` = баланс **не определён** (allows selection without displaying balance)
  * Level 3 Expanded Currency Mode: `F1 F2 F3 F4` (32-бит, big-endian)

    * `0xFFFFFFFE` = максимум “known credit” в scaled units
    * `0xFFFFFFFF` = баланс **не определён**
* **Payment Media ID:** `M1 M2 M3 M4` (32-бит, big-endian)

  * `00000000`..`FFFFFFFE` = идентификатор платежного носителя
  * `FFFFFFFF` = unknown payment media ID
* **PT — Payment Type (1 байт):**

  * `00xxxxxxb` = normal vend card
  * `x1xxxxxxb` = test media
  * `1xxxxxxxb` = free vend card
  * `xx000000b` = VMC default prices
  * `xx000001b`..`xx000100b` = user group / price list / discount / surcharge режимы (в этих режимах `PD1 PD2` трактуются как “payment data”)
* **PD1 PD2 — Payment Data (2 байта):** значение зависит от PT (например, user group / price list / discount group / percentage factor).
* **L1 L2 — User Language (только expanded):** 2 ASCII символа по ISO 639 (например, `45 4E` = "EN").
* **C1 C2 — User Currency Code (только expanded):** ISO 4217 numeric в packed BCD с ведущей цифрой `1` (например, USD = `18 40`, EUR = `19 78`).
* **OPT — Card options (только expanded):** флаги опций (например, b0=privacy: “не отображать кредит”).

**Пример Nayax (Level 2/3):** 10 03 13 88 34 31 30 38 00 00 00 → funds=0x1388, mediaID=0x34313038, PT=0x00, PD=0x0000.
**Особенности:**

* Для Cashless Device #2 все байты идентичны, отличается только префикс.
* После Begin Session ридер переходит в состояние Session Idle.

#### 9.1.5 Session Cancel Request (10 04 / 60 04)

**Описание:** Ридер просит завершить сессию досрочно (карта убрана, таймаут).
**Формат:** 10 04 (Cashless #1) или 60 04 (Cashless #2).
**Особенности:**

* VMC должен отправить 13 04 (Cashless #1) или 63 04 (Cashless #2) для завершения сессии.
* Может приходить при отключении карты или истечении таймаута ожидания выбора товара.
* Ридер ожидает завершения сессии и не перейдёт в состояние Enabled до получения SESSION Complete.
* Для Cashless Device #2 используется префикс 60 вместо 10.

#### 9.1.6 Vend Approved (10 05 AA.. / 60 05 AA..)

**Описание:** Продажа одобрена. Сумма может быть меньше запрошенной или FFFFFFFF (electronic token).
**Формат для 16-битной версии:** 10 05 AA AA (Cashless #1) или 60 05 AA AA (Cashless #2)
**Формат для 32-битной версии:** 10 05 AA AA AA AA (Cashless #1) или 60 05 AA AA AA AA (Cashless #2)

**Полный разбор байтов для 32-битной версии:**

* 10 05 или 60 05 — префикс и код события
* AA AA AA AA — одобренная сумма (big-endian) без CHK.
  **Особенности:**
* FFFFFFFF означает использование электронного токена (не денежную единицу).
* Если включён режим скидок/наценок, одобренная сумма может отличаться от запрошенной.
* После получения Vend Approved VMC должен выдать товар и отправить VEND Success.
* Для Cashless Device #2 все байты идентичны, отличается только префикс.

#### 9.1.7 Vend Denied (10 06 / 60 06)

**Описание:** Отказ в продаже (недостаточно средств, нет связи с сервером Nayax, ошибка авторизации).
**Формат:** 10 06 (Cashless #1) или 60 06 (Cashless #2).
**Особенности:**

* Причина отказа не указывается в этом событии.
* После Vend Denied ридер остаётся в состоянии Session Idle.
* Для Cashless Device #2 используется префикс 60 вместо 10.

#### 9.1.8 End Session (10 07 / 60 07)

**Описание:** Сессия успешно завершена по SESSION Complete. Ридер вернулся в Enabled.
**Формат:** 10 07 (Cashless #1) или 60 07 (Cashless #2).
**Особенности:**

* Приходит после успешного завершения сессии командой SESSION Complete.
* Ридер переходит в состояние Enabled и готов принимать новую карту.
* Для Cashless Device #2 используется префикс 60 вместо 10.

#### 9.1.9 Cancelled (10 08 / 60 08)

**Описание:** Сессия отменена (по Reader Cancel, Vend Cancel или таймауту).
**Формат:** 10 08 (Cashless #1) или 60 08 (Cashless #2).
**Особенности:**

* Возникает при отмене сессии командой READER Cancel или VEND Cancel.
* Также может приходить при таймауте сессии (зависит от реализации ридера).
* После получения Cancelled VMC должен отправить SESSION Complete для завершения сессии.
* Для Cashless Device #2 используется префикс 60 вместо 10.

#### 9.1.10 Peripheral ID (Activity: 10 09 ... / 60 09 ...)

**Описание:** Полная идентификация ридера (асинхронная передача).
**Формат для Cashless #1:** 10 09 `09 ...` (без CHK)
**Формат для Cashless #2:** 60 09 `09 ...` (без CHK)
**Полный разбор байтов:** см. описание `Peripheral ID (09h)` в разделе Reply Data (п. 8.4), но помните: здесь **нет CHK**.
**Особенности:**

* Редкое событие; чаще Peripheral ID приходит как синхронный ответ на EXPANSION Request ID (где есть CHK).

#### 9.1.11 Malfunction/Error (10 0A EE SS / 60 0A EE SS)

**Описание:** Ошибка ридера.
**Формат:** 10 0A EE SS (Cashless #1) или 60 0A EE SS (Cashless #2).

**Интерпретация:**

* `EE` = `xxxxyyyy` (старшие 4 бита `xxxx` — тип ошибки, младшие 4 бита `yyyy` — старшие биты manufacturer-defined subcode)
* `SS` = младший байт manufacturer-defined subcode
* Итоговый manufacturer subcode: `subcode = ((EE & 0x0F) << 8) | SS`

**Типы ошибок (`xxxx` в EE):**

* `0000` — Payment media Error (transient)
* `0001` — Invalid Payment media (transient)
* `0010` — Tamper Error (transient)
* `0011` — Manufacturer Defined Error (transient)
* `0100` — Communications Error (non-transient; reader still functional)
* `0101` — Reader Requires Service (non-transient; reader still functional)
* `0110` — Unassigned (non-transient; reader still functional)
* `0111` — Manufacturer Defined Error (non-transient; reader still functional)
* `1000` — Reader Failure (non-transient; reader not presently functional)
* `1001` — Communications Error (non-transient; reader not presently functional)
* `1010` — Payment media Jammed (non-transient; reader not presently functional)
* `1011` — Manufacturer Defined Error (non-transient)
* `1100` — Refund error – internal reader credit lost
* `1101`..`1111` — Unassigned

**Особенности:**

* Transient error обычно репортится до ACK’а, затем очищается.
* Non-transient error может репортиться каждый POLL до устранения.

#### 9.1.12 Command Out of Sequence (10 0B ... / 60 0B ...)

**Описание:** Команда пришла в неверном состоянии.
**Формат для Level 1:** 10 0B (Cashless #1) или 60 0B (Cashless #2)
**Формат для Level 2/3:** 10 0B CC (Cashless #1) или 60 0B CC (Cashless #2)

**Коды состояния (`CC` для Level 2/3):**

* 01 — Inactive
* 02 — Disabled
* 03 — Enabled
* 04 — Session Idle
* 05 — Vend
* 06 — Revalue
* 07 — Negative Vend
  **Особенности:**
* Сообщение означает, что reader получил команду, которую нельзя выполнить в текущем состоянии/последовательности (command должен быть ACK’нут, но не выполнен).
* В типовом сценарии VMC выполняет RESET и повторную инициализацию.
* Для Cashless Device #2 все байты идентичны, отличается только префикс.

### 9.1.13 Revalue Approved (10 0D AA.. / 60 0D AA..)

**Описание:** Пополнение (revalue) платёжного носителя одобрено (prepaid-функция). Событие означает, что ридер принял и завершил операцию пополнения на указанную сумму.
**Когда возникает:** после отправки `REVALUE Request` (`15 00 ...` для Cashless #1 / `65 00 ...` для Cashless #2) и успешной обработки ридером.
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Форматы по режимам денежных значений:**

**Вариант A — 16-bit money (Expanded Currency Mode выключен):**

* Cashless #1: `10 0D A1 A2`
* Cashless #2: `60 0D A1 A2`

Где:

* `10` / `60` — Device ID
* `0D` — Activity Code: **Revalue Approved**
* `A1 A2` — одобренная сумма пополнения **scaled**, 16-бит, **big-endian**

**Вариант B — 32-bit money (Expanded Currency Mode включён):**

* Cashless #1: `10 0D A1 A2 A3 A4`
* Cashless #2: `60 0D A1 A2 A3 A4`

Где:

* `A1 A2 A3 A4` — одобренная сумма пополнения **scaled**, 32-бит, **big-endian**

**Интерпретация суммы:**

* `A...` — **scaled value** (денежное значение в масштабированных единицах)
* Реальная сумма вычисляется по параметрам `Scale Factor (Z5)` и `Decimal Places (Z6)` из `Reader Config Data`:

  * `amountReal = amountScaled × scale / (10^decimal)`
* Специальное значение:

  * `0xFFFFFFFF` (только в 32-битном формате) может использоваться как “electronic token” / non-monetary approval (в зависимости от реализации ридера).

**Особенности обработки:**

* В сценарии пополнения VMC должен считать операцию завершённой после получения `Revalue Approved`.
* Если ридер поддерживает/использует “электронные токены”, то `FFFFFFFF` не следует интерпретировать как денежную сумму.
* Для Cashless #2 payload идентичен, отличается только Device ID.

---

### 9.1.14 Revalue Denied (10 0E / 60 0E)

**Описание:** Пополнение (revalue) отклонено. Событие означает, что ридер отказал в выполнении `REVALUE Request`.
**Когда возникает:** после отправки `REVALUE Request` и решения ридера отказать (нет карты, нет связи, лимит, отказ сервера и т.п.).
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Формат:**

* Cashless #1: `10 0E`
* Cashless #2: `60 0E`

Где:

* `10` / `60` — Device ID
* `0E` — Activity Code: **Revalue Denied**

**Особенности обработки:**

* Причина отказа в этом событии **не передаётся**.
* После `Revalue Denied` VMC должен считать `REVALUE Request` завершённым с ошибкой и не повторять запрос без изменения условий (например, без новой сессии/повторного запроса лимита).
* Для Cashless #2 payload идентичен, отличается только Device ID.

---

### 9.1.15 Revalue Limit Amount (10 0F LL.. / 60 0F LL..)

**Описание:** Асинхронная передача лимита пополнения (revalue limit). Это то же значение, что возвращается синхронно как `Revalue Limit Amount (0x0F)` в ответ на `REVALUE Limit Request`, но доставлено как activity.
**Когда возникает:** после `REVALUE Limit Request` или при необходимости уведомить VMC об изменении лимита (редко).
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Форматы по режимам денежных значений:**

**Вариант A — 16-bit money (Expanded Currency Mode выключен):**

* Cashless #1: `10 0F L1 L2`
* Cashless #2: `60 0F L1 L2`

Где:

* `L1 L2` — лимит пополнения **scaled**, 16-бит, **big-endian**

**Вариант B — 32-bit money (Expanded Currency Mode включён):**

* Cashless #1: `10 0F L1 L2 L3 L4`
* Cashless #2: `60 0F L1 L2 L3 L4`

Где:

* `L1 L2 L3 L4` — лимит пополнения **scaled**, 32-бит, **big-endian**

**Интерпретация значения:**

* `limitScaled` трактуется как максимальная сумма, которую VMC может отправить в `REVALUE Request` **в текущем состоянии**.
* Реальная сумма:

  * `limitReal = limitScaled × scale / (10^decimal)`

**Особенности обработки:**

* Если `limitScaled = 0`, пополнение фактически невозможно (либо лимит исчерпан).
* VMC должен использовать это значение как верхнюю границу для суммы `REVALUE Request`.
* Для Cashless #2 payload идентичен, отличается только Device ID.

---

### 9.1.16 User File Data (10 10 ... / 60 10 ...)

**Описание:** Данные “User File” (optional feature). Используется только при поддержке и применении User File команд из EXPANSION (например, чтение/запись пользовательского файла).
**Когда возникает:** как ответ/часть обмена при выполнении EXPANSION-команд User File (и/или как асинхронная передача данных).
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Формат (общий):**

* Cashless #1: `10 10 <payload...>`
* Cashless #2: `60 10 <payload...>`

Где:

* `10` / `60` — Device ID
* `10` — Activity Code: **User File Data**
* `<payload...>` — данные user file согласно EXPANSION User File Data форматам (длина и структура определяются конкретной командой EXPANSION, используемой VMC).

**Особенности:**

* Появляется только если включены/используются соответствующие опции и команды EXPANSION.
* Если VMC не реализует User File функциональность — событие можно игнорировать (но корректно логировать).

---

### 9.1.17 Time/Date Request (10 11 ... / 60 11 ...)

**Описание:** Событие, связанное с запросом/обменом времени и даты (optional feature). Применяется только если VMC реализует соответствующие EXPANSION команды и ридер запрашивает/передаёт time/date.
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Формат (общий):**

* Cashless #1: `10 11 <payload...>`
* Cashless #2: `60 11 <payload...>`

Где:

* `11` — Activity Code: **Time/Date Request**
* `<payload...>` — payload времени/даты согласно формату EXPANSION Time/Date (конкретная структура зависит от подтипа/команды).

**Особенности:**

* Если VMC не поддерживает Time/Date функциональность — событие можно игнорировать (но корректно логировать).
* Для корректной работы функции требуется строго следовать формату EXPANSION Time/Date сообщений.

---

### 9.1.18 Data Entry Request (10 12 ... / 60 12 ...)

**Описание:** Запрос ввода данных (Data Entry, optional feature). Используется, когда ридер требует от VMC ввода данных пользователем (например, номер телефона, PIN, подтверждение и т.п.), при условии что функция разрешена и включена через EXPANSION option bits (Data Entry).
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Формат (общий):**

* Cashless #1: `10 12 <payload...>`
* Cashless #2: `60 12 <payload...>`

Где:

* `12` — Activity Code: **Data Entry Request**
* `<payload...>` — описание поля(ей) ввода/масок/правил ввода согласно формату EXPANSION Data Entry (структура зависит от подтипа запроса).

**Особенности:**

* Возникает только при поддержке и включении Data Entry опции.
* VMC должен отобразить пользователю запрос ввода и затем отправить соответствующий ответ Data Entry через EXPANSION (согласно поддерживаемому формату).
* Если VMC не поддерживает Data Entry — корректное поведение зависит от требований сценария (обычно отмена сессии или отказ).

---

### 9.1.19 Data Entry Cancel (10 13 ... / 60 13 ...)

**Описание:** Отмена режима/процесса Data Entry (optional feature). Ридер сообщает, что ввод данных более не требуется, либо что запрос отменён.
**Формат:** всегда начинается с Device ID (10 или 60), **без CHK**.

**Формат (общий):**

* Cashless #1: `10 13 <payload...>`
* Cashless #2: `60 13 <payload...>`

Где:

* `13` — Activity Code: **Data Entry Cancel**
* `<payload...>` — может быть пустым либо содержать дополнительные параметры отмены (в зависимости от спецификации/реализации EXPANSION Data Entry).

**Особенности:**

* При получении события VMC должен прекратить отображение/ожидание ввода данных и продолжить сессию согласно состоянию (или завершить её, если это было причиной отмены).
* Если VMC реализует Data Entry, необходимо корректно синхронизировать внутреннее состояние “ожидание ввода” с этим событием.

## 10. Обработка цен (Scale Factor и Decimal Places)

Параметры **Scale Factor** и **Decimal Places** приходят в `Reader Config Data` (**Z5** и **Z6**).

**Полная формула преобразования:**

```
real_price = scaled_value * scale_factor / 10^decimal_places
scaled_value = real_price * 10^decimal_places / scale_factor
```

**Поддержка расширенных (32-битных) сумм:**
Если включён бит **b1 (32-bit money mode)** в `Enable Options (17 04 / 67 04)`:

* Scaled значения в `Begin Session`, `Vend Approved`, `Revalue` — **32-битные** (4 байта, **big-endian**).
* Максимальное значение **денежной величины**: 0xFFFFFFFF (≈42949672.95 при scale=1, decimal=2).
  При этом для некоторых полей/событий 0xFFFFFFFF может иметь **специальный смысл** (например, “balance unknown” в `Begin Session` или “electronic token” в `Vend Approved`/`Revalue` — зависит от типа поля/события и реализации ридера).

**Работа с 32-битными значениями в коде (важно):**
JavaScript bitwise операции работают с signed int32. Для корректной работы с uint32 рекомендуется использовать `DataView.getUint32()` или преобразование через `>>> 0`.

* Все 16/32-битные значения передаются в формате **big-endian** (старший байт первый).
* При работе с 32-битными значениями необходимо проверять, что:

  * ридер **поддерживает** 32-bit money mode (по `Optional Feature bits` в `Peripheral ID (09h)`, бит **b1**),
  * VMC **включил** 32-bit money mode (бит **b1** в `Enable Options (17 04 / 67 04)`).
* 32-битные денежные значения используются только на устройствах, поддерживающих Level 3/Expansion (и при включённой опции).

**Примеры преобразования:**
Nayax типичный (scale=1, decimal=2, 16-бит): scaled = 500 (0x01F4) → real = 500 * 1 / 100 = 5.00
32-бит пример: scaled = 100000 (0x000186A0) → real = 100000 * 1 / 100 = 1000.00

**Пример кода Node.js (универсальный для 16/32-бит):**

```javascript
let scaleFactor = 1;
let decimalPlaces = 2;
let is32BitMode = false; // true, если включён бит b1 в Enable Options (и ридер поддерживает b1 в Optional Feature bits)

function parseScaled(buffer, byteOffset = 0, is32Bit = is32BitMode) {
  if (!scaleFactor) throw new Error('scaleFactor must be non-zero');

  let scaled = 0;
  if (is32Bit) {
    // 32-битное значение (4 байта, big-endian) -> uint32
    scaled = (buffer[byteOffset] << 24) |
             (buffer[byteOffset + 1] << 16) |
             (buffer[byteOffset + 2] << 8) |
             buffer[byteOffset + 3];
    scaled >>>= 0; // Преобразование в беззнаковое 32-битное число
  } else {
    // 16-битное значение (2 байта, big-endian) -> uint16
    scaled = (buffer[byteOffset] << 8) | buffer[byteOffset + 1];
  }

  return (scaled * scaleFactor) / Math.pow(10, decimalPlaces);
}

function createScaled(value) {
  if (!scaleFactor) throw new Error('scaleFactor must be non-zero');

  const scaledValue = Math.round(value * Math.pow(10, decimalPlaces) / scaleFactor);

  if (is32BitMode) {
    // Возвращаем 32-битное представление (uint32)
    if (scaledValue < 0 || scaledValue > 0xFFFFFFFF) {
      throw new Error(`Value ${value} is out of uint32 range when scaled`);
    }
    const u32 = scaledValue >>> 0;
    return [
      (u32 >>> 24) & 0xFF,
      (u32 >>> 16) & 0xFF,
      (u32 >>> 8) & 0xFF,
      u32 & 0xFF
    ];
  } else {
    // Проверяем, не превышает ли значение 16-битный максимум
    if (scaledValue < 0 || scaledValue > 0xFFFF) {
      throw new Error(`Value ${value} is out of uint16 range when scaled`);
    }
    return [
      (scaledValue >>> 8) & 0xFF,
      scaledValue & 0xFF
    ];
  }
}
```

**Важные замечания по работе с 32-битными значениями:**

* 32-битный режим активируется только после включения бита **b1** в команде `Enable Options (17 04 / 67 04 ...)` (и только если ридер объявил поддержку **b1** в `Peripheral ID`).
* После включения 32-битного режима, необходимо повторно отправить `SETUP Max/Min Price` в расширенном формате.
* Все значения в 32-битном режиме должны быть в **big-endian** формате.
* При работе с 32-битными значениями в JavaScript необходимо учитывать ограничения точности целых чисел (максимальное безопасное целое — 2^53-1).

**Важно:** В `VEND Request` цена становится **32-битной** (4 байта), если активирован **32-bit money mode** через `Enable Options` (и используется expanded-формат команды); иначе цена в `VEND Request` остаётся **16-битной** (2 байта).

## Стандартный сценарий инициализации cashless-ридера (после запуска VMC или после Just Reset)

Ниже — **типовой обязательный init-flow** для каждого cashless-устройства **через MDB-RS232 мост**.
Этот блок выполняется:

* при старте системы,
* после получения activity `Just Reset (10 00 / 60 00)`,
* после обнаружения, что ридер “off-line” (нет ответов дольше `Z7`).

> Важно: все команды ниже относятся к **адресации устройства при отправке через мост** (Cashless #1 = `0x10`, Cashless #2 = `0x60`).

### ACK и NAK (коды ответа)

* **ACK** = `00`
* **NAK** = `FF`

### Инициализация Cashless #1 (адрес = 0x10)

```
[1] VMC → мост: RESET
    Команда: 10
    Данные: нет
    Ожидаемый ответ: 00 (ACK) или FF (NAK)
    Возможное activity: 10 00 (Just Reset)

[2] VMC → мост: SETUP Config Data
    Команда: 11 00 Y2 Y3 Y4 Y5
    Где:
      Y2 = VMC Feature Level (01/02/03)
      Y3 = Columns on display
      Y4 = Rows on display
      Y5 = Display Information byte
    Пример: 11 00 03 00 00 02

    Ожидаемый ответ: Reply Data "Reader Config Data"
      Payload: 01 Z2 Z3 Z4 Z5 Z6 Z7 Z8 ... CHK
      Где:
        Z2 = Feature Level ридера
        Z3 Z4 = Country/Currency Code (2 байта)
        Z5 = Scale Factor
        Z6 = Decimal Places
        Z7 = Application Maximum Response Time
        Z8 = Miscellaneous Options

    Действия VMC:
      - сохранить Z5/Z6 для всех конвертаций цен и сумм
      - сохранить Z7 как таймаут “non-response”
      - сохранить Z8 (misc options)

[3] VMC → мост: SETUP Max/Min Price (первичный, 16-bit формат)
    Команда: 11 01 XX XX YY YY
    Где:
      XX XX = Max Price (scaled, 16-бит, big-endian)
      YY YY = Min Price (scaled, 16-бит, big-endian)
    Пример: 11 01 FF FF 00 00
    Ожидаемый ответ: 00 (ACK) или FF (NAK)

[4] VMC → мост: EXPANSION Request ID
    Команда: 17 00
    Данные: нет
    Ожидаемый ответ: Reply Data "Peripheral ID (09h)"
      Payload: 09 <manufacturer(3)> <serial(12)> <model(12)> <sw(2)> [optionalFeatureBits(4)] CHK

    Действия VMC:
      - сохранить Optional Feature bits (если присутствуют)
      - определить, какие опции можно включить через Enable Options:
          b1 = 32-bit money mode (опционально)
          b5 = Always Idle mode (опционально)
          и т.д.

[5] VMC → мост: EXPANSION Enable Options (включение опций ридера)
    Команда: 17 04 B1 B2 B3 B4
    Где:
      B1..B4 = 32-битная маска (старший байт первым)
      Включаются только те биты, которые поддерживает ридер (по Optional Feature bits)

    Примеры (все варианты опциональны, выбираются по требованиям VMC):
      - Ничего не включать: 17 04 00 00 00 00
      - Включить Always Idle (b5): 17 04 00 00 00 20
      - Включить 32-bit money (b1): 17 04 00 00 00 02
      - Включить Always Idle + 32-bit money: 17 04 00 00 00 22

    Ожидаемый ответ: 00 (ACK) или FF (NAK)

[6] (только если включён 32-bit money) VMC → мост: SETUP Max/Min Price (расширенный формат)
    Условие: включён b1 (32-bit money mode)

    Команда: 11 01 XX XX XX XX YY YY YY YY CC CC
    Где:
      XX.. = Max Price (scaled, 32-бит, big-endian)
      YY.. = Min Price (scaled, 32-бит, big-endian)
      CC CC = Currency Code (ISO 4217 numeric packed BCD)
    Пример (EUR):
      11 01 FF FF FF FF 00 00 00 00 19 78
    Ожидаемый ответ: 00 (ACK) или FF (NAK)

[7] VMC → мост: READER Disable (рекомендуемый безопасный шаг)
    Команда: 14 00
    Данные: нет
    Ожидаемый ответ: 00 (ACK) или FF (NAK)

[8] VMC → мост: READER Enable
    Команда: 14 01
    Данные: нет
    Ожидаемый ответ: 00 (ACK) или FF (NAK)

[9] Ридер готов к работе
    Ожидаемые activity при использовании:
      - 10 03 ... (Begin Session)
      - 10 05 ... (Vend Approved)
      - 10 06 (Vend Denied)
      - 10 07 (End Session)
```

### Инициализация Cashless #2 (адрес = 0x60)

Полностью аналогично, но команды с префиксом `0x60`/`0x61`/`0x67`/`0x64`:

```
[1] VMC → мост: RESET
    60
    ← 00 (ACK) или FF (NAK)

[2] VMC → мост: SETUP Config Data
    61 00 Y2 Y3 Y4 Y5
    Пример: 61 00 03 00 00 02
    ← Reply: 01 ... CHK

[3] VMC → мост: SETUP Max/Min Price (16-bit)
    61 01 FF FF 00 00
    ← 00 (ACK) или FF (NAK)

[4] VMC → мост: EXPANSION Request ID
    67 00
    ← Reply: 09 ... CHK

[5] VMC → мост: EXPANSION Enable Options
    67 04 B1 B2 B3 B4
    Примеры (все варианты опциональны):
      - 67 04 00 00 00 00  (не включать опции)
      - 67 04 00 00 00 20  (Always Idle)
      - 67 04 00 00 00 02  (32-bit money)
      - 67 04 00 00 00 22  (Always Idle + 32-bit money)
    ← 00 (ACK) или FF (NAK)

[6] (только если включён 32-bit money) VMC → мост: SETUP Max/Min Price (32-bit расширенный)
    61 01 FF FF FF FF 00 00 00 00 19 78
    ← 00 (ACK) или FF (NAK)

[7] VMC → мост: READER Disable
    64 00
    ← 00 (ACK) или FF (NAK)

[8] VMC → мост: READER Enable
    64 01
    ← 00 (ACK) или FF (NAK)

[9] Ридер готов
    Activity:
      - 60 03 ... (Begin Session)
      - 60 05 ... (Vend Approved)
      - 60 06 (Vend Denied)
      - 60 07 (End Session)
```

## Сценарий обработки ошибок и повторной инициализации (recovery / re-init)

Ниже — типовой блок реакции VMC на ошибки **на уровне обмена с мостом**: **FF (NAK)**, отсутствие ответа дольше `Z7`, критические activity (`Malfunction/Error`, `Command Out of Sequence`), а также неожиданные сбросы (`Just Reset`).
Цель: вернуть ридер в рабочее состояние через корректный `RESET` и полный init-flow (см. блок выше).

> Важно: все перечисленные события/ответы рассматриваются только в контексте того, **что именно VMC получает от моста** (ACK/NAK, activity), и что VMC отправляет в мост.

---

### 1) Ошибка: NAK на команду (ответ = FF)

**Симптом:**

* VMC отправляет команду в мост, а в ответ получает **FF (NAK)**.

**Действия VMC (рекомендуемый порядок):**

1. **Остановить текущий flow** (не продолжать последующие команды сценария).
2. Если команда относится к vend/revalue сессии:

   * отправить `READER Cancel` (`14 02` для #1 / `64 02` для #2) и ожидать `activity Cancelled (10 08 / 60 08)` или `Session Cancel Request (10 04 / 60 04)`.
   * затем отправить `SESSION Complete` (`13 04` / `63 04`) чтобы закрыть контекст сессии.
3. Выполнить **полную переинициализацию**:

   * отправить `RESET` (10/60),
   * дождаться ACK,
   * далее выполнить init-flow полностью (SETUP Config, SETUP Max/Min Price, EXPANSION Request ID, EXPANSION Enable Options, повторный SETUP Max/Min Price в 32-bit если включён b1, Reader Enable).

---

### 2) Ошибка: отсутствие ответа дольше Z7 (non-response timeout / off-line)

**Симптом:**

* После отправки команды в мост VMC не получает ни `00 (ACK)`, ни `FF (NAK)`, ни ожидаемого reply/activity.
* Либо по общему мониторингу “ридер молчит” дольше `Z7` секунд (значение `Z7` из Reader Config Data).

**Действия VMC:**

1. Считать ридер **off-line**.
2. Выполнить **жёсткий recovery**:

   * отправить `RESET` (10/60) в мост,
   * дождаться ACK (или повторить RESET ограниченное число раз),
   * выполнить init-flow полностью.
3. Если после нескольких попыток init-flow ридер остаётся off-line:

   * зафиксировать ошибку,
   * пометить устройство недоступным и периодически повторять recovery (например, раз в N секунд/минут).

---

### 3) Событие: Malfunction/Error (10 0A EE SS / 60 0A EE SS)

**Симптом:**

* Мост выдаёт activity `10 0A EE SS` (или `60 0A ...`) — ошибка ридера.

**Действия VMC:**

1. Немедленно **прекратить текущие операции** (vend/revalue).
2. Если сессия активна:

   * отправить `READER Cancel` (14 02 / 64 02),
   * затем `SESSION Complete` (13 04 / 63 04) при необходимости закрытия сессии.
3. Выполнить **полный RESET + init-flow**.
4. Если ошибка повторяется:

   * фиксировать `EE SS` (тип/код) для диагностики,
   * при необходимости отключить ридер (не выполнять `READER Enable`) и перейти в режим деградации.

---

### 4) Событие: Command Out of Sequence (10 0B [CC] / 60 0B [CC])

**Симптом:**

* Мост выдаёт activity `10 0B` (Level 1) или `10 0B CC` (Level 2/3), что означает нарушение последовательности/состояния.

**Действия VMC:**

1. Считать текущий сценарий “сломавшимся” (состояния VMC и ридера рассинхронизированы).
2. Выполнить **полный RESET + init-flow**.
3. Внутри логики VMC:

   * обновить внутренний state-machine так, чтобы запрещать отправку команд “не в том состоянии” (например, `VEND Request` до готовности устройства, или `VEND Success` без `Vend Approved`).

---

### 5) Событие: Just Reset (10 00 / 60 00) в любой момент

**Симптом:**

* Мост выдаёт `Just Reset`, хотя VMC не инициировал RESET (возможен power glitch/сброс ридера).

**Действия VMC:**

1. Считать все текущие сессии/операции **прерванными**.
2. Выполнить **полный init-flow** с самого начала для соответствующего устройства:

   * SETUP Config Data,
   * SETUP Max/Min Price,
   * EXPANSION Request ID,
   * EXPANSION Enable Options,
   * при 32-bit money — повторный SETUP Max/Min Price (32-bit),
   * READER Enable.

---

### 6) Ошибка в процессе vend: Vend Denied (10 06 / 60 06)

**Симптом:**

* VMC получил `Vend Denied` после `VEND Request`.

**Действия VMC:**

1. Считать продажу отклонённой.
2. Не отправлять `VEND Success`.
3. Завершить сессию корректно:

   * отправить `SESSION Complete` (13 04 / 63 04),
   * дождаться `End Session` (10 07 / 60 07) или `Cancelled`.
4. Если `Vend Denied` повторяется систематически:

   * не выполнять RESET автоматически (это не обязательно ошибка протокола),
   * но при наличии сопутствующих `10 0A` / non-response / NAK — переходить к recovery.

---

### 7) Ошибка: Cancelled (10 08 / 60 08) в середине сценария

**Симптом:**

* Сессия была отменена (по cancel/таймауту/ошибке).

**Действия VMC:**

1. Считать текущую операцию завершённой без продажи/без пополнения.
2. Отправить `SESSION Complete` (13 04 / 63 04), чтобы закрыть контекст (если это требуется по вашей state-machine).
3. Дождаться `End Session` (10 07 / 60 07) либо перейти в “готовность”.
4. Если после Cancelled устройство не возвращается в норму — выполнить RESET + init-flow.

## Сценарий Keep-Alive / Periodic Polling (периодический опрос ридера) и контроль “offline”

Этот раздел описывает **строго корректное правило** периодического опроса (keep-alive) cashless-ридера **через MDB-RS232 мост**, чтобы ридер **не уходил в ошибку связи с VMC** и не считался “потерянным” из-за отсутствия активности со стороны VMC.

> Важно: описывается только обмен **VMC ↔ мост ↔ ридер**. Любые сценарии “VMC ↔ ридер напрямую по MDB” не рассматриваются.

---

### 1) Базовое правило keep-alive

**VMC должен регулярно получать любую валидную активность от моста**, связанную с ридером, либо инициировать такую активность периодическими командами.

Считается, что связь с ридером “живая”, если в течение окна времени, **не превышающего `Z7` секунд**, VMC наблюдает хотя бы одно из событий:

* получен `00 (ACK)` от моста на команду,
* получен `FF (NAK)` от моста на команду,
* получен `Reply Data ... CHK` (валидный по checksum),
* получено activity-сообщение `10 xx ...` (Cashless #1) или `60 xx ...` (Cashless #2).

Если **нет вообще никаких входящих данных** дольше `Z7`, ридер считается **off-line** (потеря связи/молчание).

---

### 2) Источник значения `Z7` (таймаут non-response)

`Z7` берётся из `Reader Config Data` — ответа ридера на команду:

* Cashless #1: `SETUP Config Data (11 00 ...)`
* Cashless #2: `SETUP Config Data (61 00 ...)`

Формат ответа:

```
01 Z2 Z3 Z4 Z5 Z6 Z7 Z8 ... CHK
```

`Z7` используется как **Application Maximum Response Time** — максимальное время, в течение которого ридер может **не отвечать** (ACK/NAK/Reply/Activity), после чего VMC должен считать устройство потерянным и выполнить восстановление.

---

### 3) Рекомендуемый период опроса (pollInterval)

Чтобы не приближаться к порогу `Z7`, keep-alive должен быть существенно чаще:

**Рекомендуемое правило:**

```
pollInterval = min(1 сек, Z7 / 2)
```

Практически рекомендованные значения:

* по умолчанию: `pollInterval = 1000 ms`
* если `Z7 ≤ 10 сек`: `pollInterval = 500 ms`
* если ресурсы ограничены: допускается `pollInterval = 2000 ms`, но только при `Z7` существенно больше (например 30–40 сек)

---

### 4) Команда keep-alive (что отправлять в мост)

Keep-alive команда должна быть:

* безопасной (не запускать оплату/пополнение),
* короткой,
* дающей быстрый ответ (ACK/NAK).

**Рекомендуемая keep-alive команда: `READER Enable`**

* Cashless #1: `14 01`
* Cashless #2: `64 01`

**Ожидаемый ответ от моста:**

* `00 (ACK)` — команда принята
* `FF (NAK)` — команда отклонена (команда должна быть повторена/выполнен recovery при систематическом повторении)

> Команда `READER Enable` считается идемпотентной для keep-alive: если ридер уже в Enabled — она используется как “ping” и не должна ломать рабочий режим.

---

### 5) Когда keep-alive отправлять нельзя (не мешать транзакции)

Keep-alive **не должен отправляться**, если VMC находится в активной фазе процесса (например ожидается `Vend Approved / Vend Denied`), чтобы не создавать лишнюю конкуренцию команд.

**Правило:**

* если идёт активная сессия/ожидание результата продажи (`SESSION_ACTIVE` / `VEND_IN_PROGRESS`) — keep-alive временно отключается,
* вместо этого работает только контроль таймаута: если `now - lastSeen > Z7` → recovery.

---

### 6) Модель контроля связи: lastSeen

VMC должен вести отметку времени:

* `lastSeenTimestamp`

Она обновляется **на любое входящее событие от моста**, связанное с данным ридером:

* `00 (ACK)`
* `FF (NAK)`
* `Reply Data ... CHK`
* activity `10 xx ...` / `60 xx ...`

---

### 7) Строгое правило “offline”

Если выполняется условие:

```
(now - lastSeenTimestamp) > Z7
```

то ридер считается **off-line** и VMC обязан перейти в процедуру восстановления (`recovery / re-init`).

---

### 8) Recovery / Re-init при потере связи (обязательный сценарий)

При off-line, повторяющихся NAK или критических activity-событиях (например `Malfunction/Error`, `Command Out of Sequence`) используется единый сценарий восстановления:

#### 8.1 Recovery Cashless #1

```
[1] VMC → мост: RESET
    10
    ← 00 (ACK) или activity 10 00 (Just Reset)

[2] VMC → мост: SETUP Config Data
    11 00 Y2 Y3 Y4 Y5
    ← Reply: 01 ... CHK
    (извлечь Z7, сохранить Z5/Z6)

[3] VMC → мост: SETUP Max/Min Price (16-bit)
    11 01 XX XX YY YY
    ← 00 (ACK) или FF (NAK)

[4] VMC → мост: EXPANSION Request ID
    17 00 ...
    ← Reply: 09 ... CHK (возможен multi-message, ACK 00 после блоков)

[5] VMC → мост: EXPANSION Enable Options
    17 04 B1 B2 B3 B4
    ← 00 (ACK) или FF (NAK)

[6] Если включён 32-bit money (b1):
    VMC → мост: SETUP Max/Min Price (32-bit расширенный)
    11 01 XX XX XX XX YY YY YY YY CC CC
    ← 00 (ACK) или FF (NAK)

[7] VMC → мост: READER Enable
    14 01
    ← 00 (ACK) или FF (NAK)
```

#### 8.2 Recovery Cashless #2

Полностью аналогично, но команды:

* `60`, `61 00 ...`, `61 01 ...`, `67 00 ...`, `67 04 ...`, `64 01`

---

### 9) Обработка NAK во время keep-alive

`FF (NAK)` означает, что команда не была принята.

**Рекомендуемое правило реакции:**

* если единичный `NAK` — считать, что связь есть (lastSeen обновляется), продолжить keep-alive;
* если `NAK` повторяется подряд `N` раз (например `N=3`) — выполнить recovery / re-init.

---

### 10) Рекомендуемая конфигурация “по умолчанию”

Если нужен максимально практичный и рабочий вариант “просто чтобы не отваливался”:

* keep-alive период: `pollInterval = 1000 ms`
* команда keep-alive: `READER Enable (14 01 / 64 01)`
* таймаут offline: `Z7` секунд из `Reader Config Data`
* при offline: `RESET + полный init-flow` (см. раздел 8)
